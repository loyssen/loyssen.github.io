## 2. 组织原则

### 原则一：一个模块 = 一个关注点
| 模块           | 管什么                               |
| ------------ | --------------------------------- |
| audio        | PipeWire 音频栈                      |
| nvidia       | 显卡驱动                              |
| locale       | 地区+输入法+字体                         |
| niri         | 合成器全部（键位/布局/启动链/环境变量）             |
| portal       | XDG portal 栈                      |
| security     | polkit/SSH/密钥环                    |
| unity        | Unity 开发支持（nix-ld+unfree+sandbox） |
| noctalia-dms | DMS 构建                            |
| packages     | 所有 user-facing 软件                 |
| desktop      | SDDM+主题+全局 env+数位板                |

### 原则二：什么该合？什么该拆？
| 情况 | 合还是拆 |
|---|---|
| 配置项紧密耦合，拆了反而要互相 `import` | 合 |
| 关注点完全独立（audio 和 nvidia 互不相关） | 拆 |
| 一个文件超过 200 行 | 拆 |
| 同类配置（nvim 的 10 个插件文件） | 拆（但放在独立子目录） |

### 原则三：不要超过两个层级
```
modules/audio.nix       ← 好
nixvim/plugins/lsp.nix  ← 好
modules/foo/bar/baz.nix ← 差
```

## 3. configuration.nix 只放什么

**只放"骨架"**：
- imports（组装模块列表）
- 引导、网络、主机名、时区（这些是最顶层的系统参数，没拆出去的必要）
- nix 设置（缓存镜像、overlay）
- 用户声明（users.users）

## 4. packages.nix 组织套路

你的 packages.nix 按分组注释排列（终端/浏览器/开发/工具/......）。
好处：加软件时直接找到对应分组插一行。
**坏处**：一个文件太大了（装了 13 个新包后明显膨胀了）。

未来解法（不急现在做）：拆成 `packages/cli.nix`、`packages/dev.nix`、`packages/desktop.nix`，各自导出 list，packages/default.nix 把它们拼接。

## 5. 从 GitHub 拉新的工具集成怎么加

1. flake.nix 加 input → `nix flake lock`
2. 如果对方提供 NixOS module → configuration.nix 的 imports 加一行
3. 如果对方只提供包 → `modules/packages.nix` 里 `inputs.xxx.packages.xxx.xxx`
4. 如果对方只提供程序 → 看源码找入口，或直接用 `nix run`

你的 noctalia 就是第 3 种（加在 packages.nix 最后），niri-flake 是第 2 种（有 module）。

## 6. 不要这样（常见反模式）

```nix
# ❌ 所有东西塞 configuration.nix
{ config, pkgs, ... }: {
  services.pipewire.enable = true;
  programs.niri.enable = true;
  environment.systemPackages = [ 一百个包 ];
  # ... 300 行后还在写
}
```
→ 拉个滚动条要半天，改音频害怕影响显卡配置。

```nix
# ❌ 过度拆分，模块间循环依赖
modules/
├── audio/inputs.nix
├── audio/outputs.nix
├── audio/samplerate.nix
# ... 一个 pipewire 拆 5 个文件
```
→ 改个音频要跨 5 个文件想"那个 option 写哪了？"

**黄金平衡**：每个文件 ~30-200 行，一个聚焦的主题，自己能独立讲通。

## 7. 什么时候重构

| 信号 | 行动 |
|---|---|
| 一个文件超过 200 行 | 拆分 |
| 每次加软件要翻到文件末尾看分组 | 拆分 |
| 两个文件互相引用（比如 packages 用 nvidia 的什么） | 看看能不能解耦或合并 |
| 你打开一个文件愣两秒不记得它管什么 | 加注释或拆分 |

## 8. 你的版本管理

配置在 git 下 → 好处：
- `git log` 看历史变更
- `git diff` 看"我把什么改坏了"
- commit message 当 changelog
- 推 GitHub 自动备份（你没推但随时可以）

rebase 策略：直接在 master 上 commit 就行（个人单分支
不需要 PR 那套）。但**别 amend 已经 push 出去的 commit**。

## 9. NixOS 没有的惯例（别困惑）

- 没有 `/etc/nixos/`（你的配置不在那里，它在 ~/nixos-config）
- `nixos-rebuild` 不读 `/etc/nixos/` 除非你用 `--no-flake`
- 不要改 `hardware-configuration.nix`（它头上写着 "Do not modify this file"）

## 10. 一句话

> 好结构 = 一个文件管一块、不超过两层、命名自解释。
> 你现在的 modules/ 组织已经符合这个标准。
> 以后膨胀的信号 = 200 行 / 打开愣两秒 / 分组注释太长。
