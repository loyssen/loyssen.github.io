# 01 · 为什么需要 Nix —— 传统包管理的痛点

> 上一篇：[[08-常用命令速查表]] · 下一篇：[[02-Nix核心思想-纯函数式部署]]
> 阅读前置：[[07-软件包管理的演进]]

## 1. 你先感受：三个经典灾难

### 灾难一：我要装，系统不让
```
$ sudo apt install python3-numpy
依赖冲突：python3-numpy 需要 python3>=3.12，但某个系统组件死绑 python3.11
→ 要么降级 numpy，要么冒系统崩坏风险升级 python3
```
结果：放弃装，或者用 pip/virtualenv 手动绕——然后 pip 东西和 apt 东西混在一起，更乱。

### 灾难二：为什么两台机器不一样
同事：`apt install firefox`。你也：`apt install firefox`。
他打开网页正常，你的报 SSL 错误。查了一个小时：他 2 月装的 118 版，
12 月装的 apt 给你 124 版——行为变了。系统没有"我是怎么来的"的记录。

### 灾难三：升级翻车，一夜打螺丝
周五跑 `apt upgrade`，网络断了一下。重连后续跑……
周一起来蓝屏/内核 panic。不知道什么包什么时候部分写到一半。
修了一整天，决定下周重装。

## 2. 根因：包管理器是命令式的

```bash
apt install <包>    # 这是命令：改当前系统的状态
apt remove <包>     # 也是命令：再改
apt upgrade         # 还是命令：大规模修改
```

每条命令都是对同一个全局 `/usr` 目录做增删改。**系统没有版本**这个概念——
它只有"此刻的状态"，怎么到这个状态的没人知道。

就像你手改一个图片：叠加 N 层滤镜后，说不上来原始图长什么样。

## 3. Nix 的回答：声明式 + 纯函数

```nix
# 不写"安装"命令，写"我想要什么"
environment.systemPackages = [ pkgs.firefox ];
#                               └─ 这是 firefox 的某个**具体构建**
```

Nix 的核心直觉：**把你的系统想象成一个数学函数**。
输入 = 你的配置。
输出 = 一个 `openssl dgst -sha256 配置` 就能唯一确定的系统。

从输入到输出的过程**是一个纯函数**：
- 同样的输入 → 永远得到同样的输出（确定性）
- 构建发生在隔离的沙箱里（无副作用）
- 输出存在 `/nix/store/<hash>/` 下（可寻址）
- 从不动 `/usr`（不可变）

## 4. 解决那三个灾难

**灾难一（依赖冲突）**：A 和 B 需要不同版本的 libfoo？
→ 各自指向 `/nix/store/<各自的hash>/` → 不同版本共存，互不干扰。

**灾难二（不可复现）**：你的配置 `git clone` 到新机器 → `nixos-rebuild switch`。
出来的系统**一模一样**（连 nixpkgs 版本都 pin 死在 flake.lock 里）。

**灾难三（升级翻车）**：rebuild = 生成一个**新**的系统代际，不动旧的那份。
有问题 → 重启 → 开机菜单选上一个代际 → 秒回滚。滚回后还可以 `nixos-rebuild switch --rollback` 固化。

## 5. 代价：不是免费午餐

- **磁盘**：多版本共存 = 占用变大（但有垃圾回收 + 自动去重）
- **学习成本**：你要学 Nix 语言、flakes、模块系统——这套笔记就是为此写的
- **非上游生态**：不是 deb 格式，包要 nixpkgs 维护者专门打包（13 万+已覆盖大多数；
  少数没的如 百度网盘/Unity Editor 要用 FHS 包装/外部解压）
- **外来的二进制**：默认跑不了（缺 FHS 路径）→ 要靠 nix-ld 桥接——见 [[09-运行外来二进制-nix-ld与FHS]]

## 6. 一句话

> 传统包管理是"改当前状态"，Nix 是"声明+构建+原子切换"。
> 前者灵活但脆弱（手动、不可复现、回滚困难），
> 后者严谨且坚固（声明式、可复现、随时回滚）。
> 你选的代价是学习成本——这套笔记的价值就是把成本降到最低。
