# 07 · 软件包管理的演进

> 上一篇：[[06-进程与systemd服务]] · 下一篇：[[08-常用命令速查表]]
> 这一篇回答一个根本问题：为什么 Nix 会出现？它解决了什么百年老痛？
> 读完再看 [[01-为什么需要Nix-传统包管理的痛点]] 会更深。

## 1. 石器时代：源码编译（1990s）

```bash
./configure && make && make install
```
下载源码自己编译。问题：
- 依赖要自己一个个先装好（缺 libfoo 就报错，再去编译 libfoo……）
- 装到哪、怎么卸，全靠 Makefile 自觉
- 每台机器编出来的东西可能不一样

## 2. 青铜时代：deb / rpm 包管理（1993-1997）

Debian 的 **dpkg+apt**、RedHat 的 **rpm+yum/dnf**：
- 软件打成**包**（编译好的二进制 + 元数据）
- 包管理器解析**依赖关系**自动一起装
- 集中仓库（mirror）分发，数字签名验证

```bash
sudo apt install firefox    # 至今仍是非 Nix 世界的主流
```

**遗留的痛点**（每一个你都迟早会遇到）：
1. **依赖地狱**：A 要 libfoo-1.0，B 要 libfoo-2.0，系统只能装一份 → 打架
2. **全局状态**：装包 = 往 /usr 写文件改系统，卸不干净留垃圾
3. **不可复现**：两台"都装了 firefox"的机器，版本/配置可能差很远
4. **升级即赌博**：升到一半断电/依赖冲突 → 系统半残
5. **配置漂移**：/etc 被安装脚本+手工改+N 年积累，没人说得清系统到底什么样

## 3. 白银时代：容器与应用打包（2010s）

绕开系统包管理的两种思路：

**Flatpak / Snap / AppImage**（桌面应用沙箱打包）
- 应用自带依赖，跟系统库隔离
- Flatpak 是桌面 Linux 应用生态的重要补充（Flathub 商店）

**Docker**（服务端打包）
- 整个运行环境打成镜像
- "在我机器上能跑"的终结者

它们解决了"应用隔离"，但**没有解决系统配置管理**。

## 4. 黄金时代：Nix —— 换范式（2003）

Nix 的思路不是在旧系统上打补丁，而是问：
**如果"安装软件"是一个纯函数，会怎样？**

```
构建(源码, 依赖, 编译选项) → /nix/store/<hash(所有输入)>-<名字>/
```

- 输入不变 → 输出必然相同（**可复现**）
- 输出路径由输入的哈希决定 → 不同版本/配置**天然共存**（无依赖地狱）
- 安装 = 生成 store 路径 + 建符号链接 → **原子操作**，失败无副作用
- 卸载 = 删符号链接，垃圾回收清 store → **无残留**

系统层面 NixOS 更进一步：**整个系统是一个函数输出**：
```
nixosSystem(你的配置.nix) → /nix/store/<hash>-nixos-system-.../
```
配置即系统，系统即配置。见 [[02-Nix核心思想-纯函数式部署]]。

## 5. 各方案对照表

| 维度    | apt/dnf | Flatpak | Docker     | Nix/NixOS     |
| ----- | ------- | ------- | ---------- | ------------- |
| 依赖冲突  | 有       | 无（自带依赖） | 无          | 无（哈希隔离）       |
| 系统可复现 | ❌       | 不涉及     | 镜像级        | ✅ 整个系统        |
| 回滚    | 难       | 可以      | 镜像切换       | ✅ 开机选代际       |
| 磁盘占用  | 省       | 费（重复依赖） | 费          | 中（store 去重共享） |
| 配置管理  | 手动 /etc | 不涉及     | Dockerfile | ✅ 声明式         |
| 学习成本  | 低       | 低       | 中          | 高             |
| 外来二进制 | 直接跑     | —       | —          | 要 nix-ld/打包   |

## 6. 在 NixOS 里它们的角色

- **nixpkgs**（首选）：13 万+ 包，你能想到的几乎都有 → `modules/packages.nix`
- **Flatpak**：补 nixpkgs 没有的商业软件（可后加，一行开启）
- **Docker/podman**：跑服务（如 SQL Server 容器）、跑别人的开发环境
- **AppImage**：`appimage-run` 兜住（nix-ld 已配好，大多能直接跑）
- **手打 FHS 包装**：像 unityhub 那样给顽固二进制造个"传统 Linux 温室"

## 7. 实用：找包的正确姿势

```bash
# 网页（最快最直观）：https://search.nixos.org/packages
# 命令行搜索
nix search nixpkgs 关键词
# 精确验证某包存在且可用
nix eval --impure --expr '...tryEval pkgs.<名>.version...'  # 见踩坑记录
```

找到后加进 `modules/packages.nix` 对应分组 → rebuild → 完事。
没有 stable 或太旧 → `pkgs.unstable.<名>`（overlay 已配好，见 [[配置详解]]）。

## 8. 一句话总结

> 包管理四十年：从"自己编译"到"仓库安装"到"沙箱打包"到"函数式部署"。
> Nix 不是又一个包管理器，而是第一个把"系统"当纯函数输出的操作系统。
> 你经历的所有坑（Unity、QQ404……）都是"旧世界二进制"撞上"新世界秩序"的摩擦，
> 而 nix-ld/FHS 包装就是两个世界之间的翻译层。
